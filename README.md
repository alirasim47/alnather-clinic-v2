# عيادة الناظر — نظام إدارة عيادة البصريات

تطبيق عربي RTL لإدارة المرضى والفحوصات والمراجعات والمنتجات والعدسات بالقياس والفروع والمبيعات والعوائد والمصاريف والتقارير. البيانات تُقرأ وتُكتب عبر خادم Next.js إلى PostgreSQL؛ لا يعتمد تسجيل الدخول أو السجلات التشغيلية على `localStorage`. يدعم تسجيل الدفعات الأولية واللاحقة للفواتير ذات الرصيد مع حفظ كل دفعة وسجلها.

## المتطلبات

- Node.js 20 أو أحدث (صورة Docker مبنية على Node 20).
- PostgreSQL 16 أو خدمة PostgreSQL متوافقة.
- HTTPS ونطاق أو عنوان ثابت عند إتاحته عبر الإنترنت.

## التشغيل الموصى به عبر Docker Compose

1. أنشئ ملف البيئة المحلي، ثم عدّل كل القيم التجريبية فيه. لا ترفع `.env` إلى Git:

   ```bash
   cp .env.example .env
   ```

   استخدم كلمة مرور عشوائية قوية لقاعدة البيانات من أحرف وأرقام فقط (لأنها جزء من عنوان اتصال Compose)، وكلمة مرور مدير لا تقل عن 16 محرفًا وتضم ثلاث فئات أحرف على الأقل. اجعل `CLINIC_SLUG` رمزًا فريدًا من 3–50 حرفًا إنجليزيًا صغيرًا أو رقمًا أو شرطة، مثل `alnather`.

2. ابنِ التطبيق وشغّله:

   ```bash
   docker compose up -d --build
   ```

   يطبّق التطبيق migrations المتسلسلة عند بدء التشغيل. منفذ PostgreSQL في Compose مرتبط بـ `127.0.0.1` فقط، ولا يُنشر على الإنترنت.

3. أنشئ أول حساب مدير مرة واحدة:

   ```bash
   docker compose run --rm setup
   ```

   تستخدم خدمة `setup` كلمة مرور المدير لمرة واحدة ولا تمررها إلى حاوية التطبيق الدائمة. يرفض الإعداد إعادة تهيئة `CLINIC_SLUG` موجود، ولا ينشئ كلمة مرور افتراضية. استخدم اسم المستخدم ورمز العيادة وكلمة المرور التي أدخلتها في `.env` لتسجيل الدخول.

4. عند استضافة التطبيق خلف وكيل عكسي يدعم HTTPS، حدّث `.env` قبل إعادة تشغيله:

   ```env
   APP_ORIGIN=https://clinic.example.com
   COOKIE_SECURE=true
   ```

   وجّه الوكيل العكسي إلى منفذ التطبيق المحلي. لا تفتح منفذ PostgreSQL على الإنترنت، واستخدم جدارًا ناريًا وTLS وتجديدًا للشهادات. القيمة الافتراضية في Compose وملف البيئة النموذجي هي `COOKIE_SECURE=true`. للتطوير المحلي عبر HTTP فقط، غيّرها صراحةً إلى `false` مع `APP_ORIGIN` على `localhost` أو عنوان loopback؛ الخادم يفرض Secure عند أي أصل خارجي حتى لو وصلت إليه `false` بالخطأ. يضيف Next سياسة CSP ورؤوس منع التأطير وMIME sniffing وحماية المُحيل والأذونات؛ تسمح CSP حاليًا بخطوط Google وأيقونات cdnjs وصور HTTPS/البيانات، وتستخدم `unsafe-inline` لسكربتات hydration التي يولدها Next، مع `unsafe-eval` للتطوير فقط. يُرسل HSTS ومنع التأطير في الإنتاج فقط. سياسة nonce أشد وتبقى تحسينًا لاحقًا.

## ربط Supabase للإنتاج

يستخدم التطبيق اتصال PostgreSQL خادميًا عبر `pg`، وليس Supabase Auth أو مفاتيح المتصفح. أنشئ مشروع Supabase مخصصًا للإنتاج، واختر منطقة قريبة من المستخدمين ومتوافقة مع متطلبات موقع البيانات. منطقة Frankfurt (`eu-central-1`) خيار قريب للعراق، لكن اختيارها ليس إثبات امتثال قانوني. لا تستخدم Free لبيانات عيادة حقيقية: المشاريع المجانية قد تتوقف بعد أسبوع خمول ولا تشمل نسخ PostgreSQL اليومية. راجع السعر والنسخ والقيود قبل أي ترقية.

من إعدادات قاعدة البيانات في Supabase اختر **Transaction Pooler** وانسخ عنوان الاتصال الكامل إلى سر الإنتاج `DATABASE_URL` لدى مضيف التطبيق، لا إلى Git أو متغيرات واجهة المتصفح. هذا مناسب لخادم قابل للتوسع أفقيًا؛ نفّذ فقط استعلامات التطبيق ومعاملاته المعتادة عبره، ولا تعتمد على session state. مهاجر المخطط يستخدم `pg_advisory_xact_lock` داخل معاملة حتى تبقى عملية الترحيل متماسكة مع transaction pooling عند تشغيل أكثر من نسخة. صورة الإنتاج تفرض TLS والتحقق من الشهادة افتراضيًا وتبدأ بحجم اتصال محدود؛ Compose المحلي يضبط SSL صراحةً على false لقاعدة التطوير المحلية.

اضبط `APP_ORIGIN` على أصل HTTPS الكامل للتطبيق المنشور (مثل `https://clinic.example.com`) حتى تُرفض عمليات التغيير القادمة من مصدر آخر، واترك `COOKIE_SECURE=true`. شغّل الترحيلات على قاعدة إنتاج فارغة قبل إنشاء حساب المدير الأول، ثم أنشئه مرة واحدة بكلمة مرور عشوائية قوية عبر بيئة/سر مؤقت آمن؛ لا تضف كلمة المرور إلى Docker image أو سجل البناء، ولا تشغّل `db:seed-admin` مع كل نشر. لا تُدخل بيانات حقيقية حتى تنجح اختبارات الاتصال وhealth والدخول والنسخ والاستعادة ومراجعة الخصوصية.

توفر نسخ Supabase التلقائية، إن كانت ضمن الخطة، حماية مفيدة لكنها لا تستبدل النسخة الخارجية المشفرة واختبار الاستعادة الدوري. كل أسرار قاعدة البيانات تبقى على الخادم ولا ترسل للمتصفح.

## التطوير المحلي دون Docker للتطبيق

شغّل PostgreSQL محليًا أو عبر Docker، واضبط `DATABASE_URL` على عنوان يمكن لجهاز التطوير الوصول إليه (غالبًا `localhost` إذا استُخدم منفذ محلي). ثم:

```bash
npm ci
npm run db:migrate
npm run db:seed-admin
npm run dev
```

لإنشاء حساب مدير لأول مرة فقط، يجب ضبط `CLINIC_NAME` و`CLINIC_SLUG` و`ADMIN_NAME` و`ADMIN_USERNAME` و`ADMIN_PASSWORD` في البيئة قبل تشغيل سكربت الإعداد. يجب أن تتكون كلمة المرور من 16 محرفًا على الأقل وثلاث فئات أحرف على الأقل (أحرف صغيرة/كبيرة/أرقام/رموز)؛ يرفض السكربت قيم placeholder الظاهرة في `.env.example`. لا تستخدم كلمة مرور حقيقية في سجل الطرفية أو ملف ملتزم إلى Git.

أوامر قاعدة البيانات:

```bash
npm run db:migrate
npm run db:seed-admin
```

## إعدادات الأمان والحدود التشغيلية

- كل قراءة وكتابة محمية بجلسة خادمية وملف تعريف ارتباط `httpOnly`، وتُفحص الصلاحيات وعزل العيادة في API. تنتهي الجلسة بعد 30 دقيقة من الخمول وبحد مطلق قدره 12 ساعة؛ يسجل الخادم النشاط، ويبطل تسجيل الخروج الجلسة في قاعدة البيانات، كما يُبطل تغيير كلمة المرور كل جلسات المستخدم. تُخزّن كلمات المرور كـ bcrypt hashes.
- يقيّد النظام عرض وتعديل البيانات حسب الفرع؛ يجب على المدير ربط كل موظف بفرع قبل استخدامه. المنتجات والفاحصون قائمة على مستوى العيادة، بينما سجلات المرضى والمبيعات والمصاريف مقيدة بالفرع.
- أول مدير يُنشأ عبر `db:seed-admin`. لا توجد بيانات اعتماد افتراضية؛ احمِ ملف `.env` وبيانات الدخول، وغيّر كلمة المرور إذا اشتبهت بتسربها.
- تصدير JSON من الإعدادات هو **تصدير لبيانات التشغيل** وليس بديلًا كاملًا عن `pg_dump`: لا يتضمن كلمات مرور أو جلسات أو سجل التدقيق، ولا يعيد طلبات النقل التاريخية عند الاستيراد. يعرض الاستيراد معاينة، ويتجاوز السجلات الموجودة ولا يستبدلها؛ تُتجاوز حسابات الموظفين لأسباب أمنية.
- قيمة «طريقة معالجة العائد» تحفظ للتوثيق فقط؛ التطبيق لا ينفذ ردًا نقديًا أو تحويلًا بنكيًا آليًا. يحدّث قيمة العائد والمخزون، ويجب تنفيذ أي رد مالي خارجيًا ومطابقته مع سجلات الدفع.
- أنشئ نسخ PostgreSQL احتياطية مشفرة ومجدولة خارج الخادم، واختبر استعادتها دوريًا. بيانات قاعدة البيانات في Compose محفوظة في volume محلي، لكن الـ volume وحده ليس نسخة احتياطية.
- لا تضع بيانات مرضى حقيقية قبل ضبط HTTPS و`APP_ORIGIN` و`COOKIE_SECURE`، وسياسات النسخ والاستعادة، وتقييد الوصول للخادم، والتحقق من الإعداد المنشور والامتثال للمتطلبات المحلية لحماية البيانات الصحية.
- صور المنتجات تُحفظ كرابط صورة اختياري، وليست خدمة تخزين ملفات مستقلة.

## مخزون العدسات المقاسة ونقطة البيع

يُعرّف سجل العدسة بفرع وعلامة ورمز اختياري، ونوع/جهة الاستخدام، ودرجة SPH وCYL وAXIS وADD، إضافة إلى المادة ومعامل الانكسار والقطر والطلاء عند إدخالها. يقبل SPH/CYL/ADD خطوات 0.25، ويُلزم AXIS بقيمة صحيحة من 0 إلى 180 عند وجود CYL غير صفري. يمكن تحديد حد تنبيه لكل درجة، والبحث والتصفية حسب الفرع وحالة الرصيد.

تبدأ نافذة البيع باختيار الفرع والمراجع اختياريًا، ثم تعرض المنتجات والخدمات ودرجات العدسات المتاحة في ذلك الفرع. عند اعتماد البيع يتحقق الخادم من الصلاحية والفرع والرصيد، ويخصم كمية العدسة ضمن معاملة الفاتورة نفسها؛ تُحفظ الدرجة والوصف مع سطر الفاتورة وتصل إشعارات تحديثها إلى الشاشة المفتوحة. يعرض التطبيق المرجعي الذي تمت مراجعته تدفق المراجع ثم المنتجات، ونموذج منتج يتضمن النوع والفئة والرمز وتنبيه المخزون والسعر ودفعة البداية؛ لم يظهر فيه مخزون درجات عدسات تفصيلي، لذا أُعيد استخدام هذه الأنماط التنظيمية مع منظومة قياس ومخزون خاصة بالمشروع، دون نسخ علامته أو أصوله.

## البنية

- `app/` — صفحات Next.js وواجهات REST في `app/api/`.
- `components/` — التخطيط العربي ومكوّنات النماذج.
- `screens/` — شاشات التشغيل.
- `lib/server/` — الجلسات والوصول والبيانات والمبيعات والمخزون والاستيراد.
- `migrations/` — ترحيلات PostgreSQL المتسلسلة.
- `scripts/` — مشغّل الترحيلات وتهيئة المدير الأول.
- `Dockerfile` و`docker-compose.yml` — صورة التطبيق وشبكة قاعدة البيانات المحلية.
